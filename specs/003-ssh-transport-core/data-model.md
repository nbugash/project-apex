# Data Model: SSH Transport Core

**Branch**: `feature/F001-ssh-transport-core` | **Date**: 2026-09-22 | **Plan**: [plan.md](./plan.md)

Entities this feature introduces. Nothing here is persisted — the transport's state dies with
the process, by design (see plan.md, Technical Context: Storage).

The wire format's own constants — frame cap, error codes, method shapes — are **not**
restated here. §4 of the system specification owns them; see research.md, "Where the
protocol's constants live".

---

## RequestId

Identifies one request for the life of one session.

| Field | Type   | Rules                                                                                     |
| ----- | ------ | ----------------------------------------------------------------------------------------- |
| value | string | Non-empty. Unique within a session (§4.2). Generated by the transport, never by a caller. |

**Why the transport generates it**: a caller that chose its own id could collide with another
caller's. Uniqueness is a property of the registry, so the registry mints it.

---

## Priority

Which class of traffic a request belongs to.

| Variant       | Meaning                                                                 |
| ------------- | ----------------------------------------------------------------------- |
| `Interactive` | The user is waiting. Completions, diagnostics, a file they just opened. |
| `Background`  | Nobody is waiting. Prefetch, indexing status, warming the cache.        |

Stated by the caller, never inferred — see research.md, "Priority classification of outbound
traffic". Ordering is total between classes and FIFO within one.

---

## PendingRequest

One request awaiting its reply. Owned by the registry; exists only between send and outcome.

| Field     | Type            | Rules                                                              |
| --------- | --------------- | ------------------------------------------------------------------ |
| id        | RequestId       | The registry's key.                                                |
| priority  | Priority        | Fixed at send time.                                                |
| deadline  | instant         | Now + the time limit. Default 30 s (FR-012), overridable per call. |
| responder | one-shot sender | Resolved exactly once, by exactly one of the outcomes below.       |

**Invariant**: registered **before** the frame is written (FR-011), so a reply cannot arrive
before the registry can match it.

**Invariant**: removed on every outcome, without exception (FR-013). A registry that retains
resolved requests is a leak that grows with session length — SC-005 measures it.

---

## RequestOutcome

Exactly one of these resolves a `PendingRequest`. The set is closed.

| Variant            | Cause                                                              |
| ------------------ | ------------------------------------------------------------------ |
| `Answered(result)` | A reply arrived carrying a result.                                 |
| `Failed(error)`    | A reply arrived carrying an error, or the frame could not be sent. |
| `TimedOut`         | The deadline passed with no reply.                                 |
| `Withdrawn`        | The caller cancelled (FR-014).                                     |
| `ConnectionLost`   | The link died while this request was outstanding (FR-020).         |

**Why `ConnectionLost` is distinct from `Failed`**: the caller can retry a `ConnectionLost`
once the link returns, and usually should. A `Failed` means the remote side considered the
request and refused it; retrying repeats the refusal.

---

## ConnectionState

Extends F000's existing enum. The interface already renders this; the new variants give it
something truthful to say during recovery.

| Variant                         | Meaning                                                     | Existing?        |
| ------------------------------- | ----------------------------------------------------------- | ---------------- |
| `Unknown`                       | Not yet attempted.                                          | Existing (F000)  |
| `Connecting`                    | An attempt is in progress.                                  | Existing (F000)  |
| `Connected`                     | Established and usable.                                     | Existing (F000)  |
| `Disconnected`                  | Not connected, not trying.                                  | Existing (F000)  |
| `Retrying { attempt, next_in_secs }` | Lost, and the supervisor is backing off before another try. | **New** (FR-020) |

**Transitions**:

```
Unknown ──────→ Connecting ──→ Connected
                    │              │
                    │ auth failed  │ loss detected
                    ↓              ↓
              Disconnected ←── Retrying ──→ Connecting
                    ↑              │
                    └── user stops ┘
```

`Retrying` carries the attempt count and how long until the next try, because "reconnecting"
with no sense of progress is indistinguishable from a hang — which is the complaint F000's
hidden window taught this project to take seriously.

---

## FailureCondition

The closed set from §3.4. A failure that does not classify is itself a defect (spec, Key
Entities), so the set includes `Unknown` to make that visible rather than silently mapping it
onto a neighbour.

| Variant                | Signal                            | Response                                 |
| ---------------------- | --------------------------------- | ---------------------------------------- |
| `HostUnreachable`      | exit 255 + timed out / refused    | Retry with backoff                       |
| `AuthenticationFailed` | exit 255 + permission denied      | Assisted attempt, then the picker        |
| `HostKeyChanged`       | exit 255 + identification-changed | **Refuse.** Warn explicitly; never retry |
| `EngineMissing`        | exit 127                          | Hand to F002; do not retry               |
| `EngineCrashed`        | non-zero, not 255                 | Restart with backoff                     |
| `NetworkDropped`       | stdout EOF, or keepalive expiry   | Retry with backoff                       |
| `Unknown`              | anything else                     | Surface verbatim; do not retry           |

**`HostKeyChanged` never retries.** Retrying a possible machine-in-the-middle is worse than
failing, and an IDE that keeps trying trains the user to dismiss the warning — §3.9's whole
concern.

**Locale independence**: classification runs against stderr produced under `LC_ALL=C` (§3.4)
and must be identical under any system language (SC-008).

---

## ConnectionAttempt

One pass through the connect sequence. Not persisted; exists for the life of an attempt.

| Field   | Type                                            | Rules                          |
| ------- | ----------------------------------------------- | ------------------------------ |
| phase   | `Silent` \| `Assisted` \| `Picker`              | §3.3's three phases, in order. |
| outcome | `Established` \| `FailedWith(FailureCondition)` | —                              |

**Rule**: `Assisted` is entered **only** from `AuthenticationFailed` (FR-006). An unreachable
host or a missing engine must never raise a passphrase prompt — prompting for a credential
when the problem is the network teaches the user their credential is wrong.

---

## Relationships

```
ConnectionAttempt ──produces──→ ConnectionState
                   └─on failure─→ FailureCondition

PendingRequest ──keyed by──→ RequestId
               ──carries───→ Priority
               ──resolves to→ RequestOutcome (exactly one, exactly once)

Registry ──owns──→ 0..n PendingRequest
SendQueue ──orders─→ 0..n outbound frames by Priority
```

**The registry and the send queue are separate.** A request is registered before it is
queued, and the queue may still hold it when the reply path is already listening. Merging
them would make FR-011's ordering guarantee — register, then write — impossible to state.
